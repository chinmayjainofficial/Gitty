= Commit Objects

== Purpose

A commit object records a repository snapshot and metadata about a commit. Its
content identifies a root tree, may identify a parent commit, and contains
author, committer, timestamp, and message fields.

The constructor is `commitObject` in `src/objects/commit.objects.ts`. It wraps
the caller-provided commit content in a commit-type header and returns the
complete object buffer. It does not itself create the content fields, hash the
object, compress it, store it, or update a branch.

== Commit object structure

The complete object buffer has this outer structure:

[source,text]
----
commit <content-size>\0<commit-content>
----

The header contains the object type `commit`, the byte length of the
commit-content buffer, and a null-byte separator. The bytes after the
separator are the commit content supplied to the constructor.

The constructor implementation is:

[source,typescript]
----
export function commitObject(commitContent: Buffer): Buffer {
    const header = `commit ${commitContent.length}\0`;
    return Buffer.concat([Buffer.from(header), commitContent]);
}
----

It uses `Buffer.length`, so the size is measured in bytes, not characters.
The commit content is concatenated as a buffer and is not converted or
normalized by the constructor.

== Commit content generated by current callers

The commit-construction paths currently provide textual content in this
order:

[source,text]
----
tree <tree-id>
parent <parent-commit-id>    (when a parent is included)
author <name> <email> <timestamp>
committer <name> <email> <timestamp>

<commit-message>
----

The `tree` line identifies the snapshot represented by the commit. A `parent`
line connects it to an earlier commit. The author and committer lines are
followed by a blank line, then the message. The constructor does not parse or
validate these lines; they are simply the bytes provided by the caller.

== Internal constructor behavior

When `commitObject(commitContent)` is called, it:

. Reads the length of the supplied `Buffer`.
. Builds a header containing `commit`, a space, that length, and a null byte.
. Converts the header text to a buffer.
. Concatenates the header buffer with the original commit-content buffer.
. Returns the resulting complete object buffer.

The function is intentionally a serializer for the outer object envelope. It
has no filesystem access and no error handling of its own.

== Commit creation paths

=== `commitCmd`

`src/commands/commit-file.commands.ts` implements the regular commit flow:

. Validates that a non-empty message was supplied and that a `.gitty`
  directory exists.
. Calls `writeTreeCmd` to snapshot the working directory and obtain the root
  tree ID.
. Reads `HEAD` to determine the current branch or detached-HEAD state and
  locates a parent commit when one exists.
. If the parent commit already refers to the same tree, reports that there is
  nothing to commit.
. Builds the commit-content buffer, including a `tree` line, an optional
  `parent` line, author and committer lines, a blank line, and the message.
. Passes that buffer to `commitObject`.
. Hashes and compresses the complete object, stores it under
  `.gitty/objects/<first-two-id-characters>/<remaining-id-characters>`, and
  updates the current branch reference or detached `HEAD` to the new commit
  ID.

Unlike the lower-level `commit-tree` implementation, this path allows the
first commit to have no parent. It is also the path that updates the current
reference after writing the commit.

The author and committer identity are currently hard-coded as
`Authorname <authoremailid@gmail.com>`. The timestamp is generated at runtime
as Unix seconds followed by `+0000`. The same timestamp is used for author and
committer. The message is followed by a newline in the commit content.

=== `commitTreeCmd`

`src/commands/tree/commit-tree.command.ts` is another caller of
`commitObject`. It requires a tree ID, parent ID, and message, and builds
content containing both `tree` and `parent` lines followed by the same
hard-coded author/committer identity and generated timestamp.

It then:

. Wraps the content with `commitObject`.
. Hashes the complete object using `hashFileObject`.
. Compresses the object with zlib.
. Stores it in `.gitty/objects` under the path derived from its hash, unless
  the object file already exists.
. Writes the resulting commit ID to standard output.

This command creates an object only. It does not update `HEAD` or a branch
reference. It also does not support a root commit because its implementation
rejects a missing parent ID.

The `commit-tree` CLI dispatcher in `index.ts` additionally attempts to check
the tree and parent object IDs before calling `commitTreeCmd`. Its
`objectExists` helper currently does not return the result of
`fs.existsSync`, so those checks do not work as intended and valid IDs are
rejected before the constructor path is reached.

== Hashing and storage

Callers hash the complete buffer returned by `commitObject`, including the
`commit <size>\0` header. The object ID therefore depends on the complete
serialized commit bytes. Differences in the tree ID, parent, identity,
timestamp, or message produce different commit content and consequently a
different hash.

The hash is a content-derived identifier; it is not assigned sequentially.
Callers compress the complete buffer for storage, while the hash is calculated
from the uncompressed bytes. The conventional object path used by these
callers is:

[source,text]
----
.gitty/objects/<first-two-id-characters>/<remaining-id-characters>
----

When the target object path already exists, the callers skip writing another
copy. The constructor itself knows nothing about IDs or paths.

== What the constructor does not do

`commitObject` only assembles the outer commit object buffer. It does not:

* Generate or validate a tree ID, parent ID, identity, timestamp, or message.
* Determine whether a parent is required.
* Parse or validate the commit-content syntax.
* Calculate the object ID.
* Compress or persist the object.
* Update `HEAD` or a branch reference.

Those responsibilities belong to the commit-creation callers and related
helpers.

== Implementation reference

* `src/objects/commit.objects.ts` adds the commit object header and combines
  it with caller-provided content.
* `src/commands/commit-file.commands.ts` creates a commit from a working-tree
  snapshot and updates the current reference.
* `src/commands/tree/commit-tree.command.ts` creates and stores a commit
  object without moving a reference.
* `src/utils/hashing/hashFileObject.utils.ts` hashes complete object buffers.
* `index.ts` dispatches the `commit-tree` command and parses its arguments.
